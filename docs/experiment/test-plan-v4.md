# Test plan: does the CCBL pipeline change what gets built?

> **Draft, not agreed.** Mike and Garry, 29 Sep 2026. Replaces v3 (see page history).

## Summary

We give one feature request to an AI coding agent in four ways and compare what it builds.
Three ways use the CCBL pipeline, which turns the request into a spec and tickets before any
code is written. The fourth way prompts the agent directly. We score every build against an
answer key that we agree before any run.

## Background

- **Monica** is an open-source personal relationship manager (PHP, Laravel, Vue). We use the
  GMT fork as a realistic existing codebase.
- **CCBL** is our method. Skills turn a request into a product spec (`create-spec`) and then
  into tickets (`create-tickets`). A person approves each step. Context documents, such as
  strategy and architecture, inform the skills.
- **The fence rule** is one instruction in `create-spec`: use the architecture document as
  guidance, but don't copy build details into the spec. In an earlier experiment that
  looked at documents only, it cut build details in tickets from 11 to 0. Each context
  document can be left out, included, or included behind a fence. This round tests that
  choice for the architecture document; later rounds can test other documents.
- **The 2 July attempt** produced one build but no answer key. We couldn't tell drift from
  correct behaviour. This plan fixes that.

## Questions

1. Does giving the spec step an architecture document change the code? Does the fence rule
   help?
2. Does the pipeline beat prompting the agent directly?

## Features

Each feature starts from a **seed**: the request in a stakeholder's words, with no build
details.

| Feature | Purpose | Seed |
|---|---|---|
| **Pilot:** download a contact as JSON | Tests the process. Results don't count: the feature is small, and a public solution exists upstream (monicahq/monica #7930) | "People who use Monica have asked for another way to get a contact's details out. Today you can download a contact as a vCard. That works for address books, but people who want to use their contact data in other tools or in their own scripts find vCard hard to work with. They would like to download a contact as JSON too, from the same place they download the vCard." |
| **Test:** download a contact's full record | The results we report. More real decisions for the agent to get right or wrong | "People want to take a full copy of a contact out of Monica. The vCard download only gives the address-book details. They want everything they have recorded about that person: notes, relationships, reminders and important dates. They want it as a file they can keep or use in other tools, downloaded from the contact's page." |

## Arms

| Arm | Branch name | Steps | Architecture document | Fence rule |
|---|---|---|---|---|
| 0a: Prompt only | `prompt_only` | Seed → code | No | – |
| 0b: Prompt + plan | `prompt_plan` | Seed → plan → code | No | – |
| A: No architecture | `no_architecture` | Seed → spec → tickets → code | No | – |
| B: Architecture | `with_architecture` | Seed → spec → tickets → code | Yes | Off |
| C: Fenced architecture | `fenced_architecture` | Seed → spec → tickets → code | Yes | On |

Code-stage branches are named `exp/<feature>/<branch name>`, for example
`exp/full-record/fenced_architecture`. See `runs/README.md`.

Only one thing changes between arms A, B and C. Every arm gets the same model, seed and
strategy document. The architecture document is Garry's (`Arch_1`). A later arm repeats C
with an architecture document generated by `bootstrap`, to compare the two.

**Model.** Every stage uses `claude-opus-5-5`, set by its full model ID with Claude Code
2.1.284, installed for the experiment only. Each run records the model it actually used.

## How each run works

1. Start from a clean copy of the repository at a tagged commit. The copy contains no other
   runs' files and no personal skills or settings.
2. Give the arm the seed.
3. The agent writes a spec and tickets, or a plan for arm 0. A person answers the agent's
   questions from a fixed answer sheet only.
4. A person approves the output unchanged. Any edit is logged.
5. The agent writes code until its own tests pass, or for 60 minutes at most.
6. Save the transcript, token count and time for each step.

Each arm runs three times, because the agent gives different output each time.

## How we score

- **Intent reference.** The answer key, written before any run. It has two parts: a list
  of 20 to 30 decisions with the right answer for each, such as who can export and which
  fields to include; and hidden acceptance tests for the parts that tests can check.
- **Intent diff.** The comparison of one build against the intent reference. It gives each
  decision one result: *matched*, *changed and flagged*, *changed silently*, or *missing*.
  It also lists anything built that the reference didn't ask for.
- **Headline number.** From the intent diff: silent changes per build that either affect users or are hard to undo.
- **Also measured.** Build details that
  leak into tickets; tokens; time, including human time; and code checks (PHPStan, Psalm,
  Pint).
- **Blind scoring.** Scorers don't know which arm produced a build.

**First result.** We scored the 2 July build against the pilot answer key in about 20
minutes. It looks clean, but it made three silent changes: it dropped the display name, added
four unrequested fields, and exported every date instead of the birthday only.

## Predictions

- Arm C leaks the fewest build details and makes the fewest silent changes.
- Arms A to C cost more tokens and human time than arm 0, and pass more hidden tests.

We report against ourselves if any of these happen:

- Arm C scores no better than arm B on the answer key.
- Arm 0 comes within one silent change of the best pipeline arm, at lower cost.
- All builds score within noise of each other. In that case, we rerun with a larger feature.
